# Mesh Discord Routing

This skill lets agents of any runtime communicate with each other through Discord using simple, explicit routing rules.

Activate this skill when a Discord message contains `cc-mesh:` or when the conversation is explicitly in mesh mode.

`cc-mesh:` means "this message is intended for these recipient labels". It is not a permanent route and it does not decide who you must write to next.

For multi-turn workflows, use a workflow state file or the bundled
`mesh-session` helper to decide the next recipient. `cc-mesh:` remains only the
transport trigger and must not be treated as turn-order memory.

When you reply in mesh mode:

- Decide who should receive your reply.
- By default, include the sender of the message you are answering.
- Add other bots only when you want to involve them.
- Use no recipients only when your reply should not notify another bot.
- Never hand-write raw Discord mentions such as `<@...>`.
- Never send a bare `cc-mesh:` / `ccm:v1` line that has not been generated by a mesh send
  tool, `mesh-hydrate`, or the bundled script.
- Prefer a native mesh send tool/API when one exists. For runtime-b, use `mesh_send`
  with semantic `to` labels, `from_label`, `mesh_id`, `body`, `target`, `format`,
  and `dry_run`; it resolves participant labels and inserts real Discord mentions
  only in the outbound payload.
- If the Agent Mesh repo helper `scripts/mesh-send-discord.mjs` is available,
  prefer it for terminal-based sends. Use `--dry-run` first; real sends require
  `--send` plus `DISCORD_BOT_TOKEN`. It supports `--to`, `--from`, `--id`,
  `--body`, `--target discord:<channel>[:thread]`, `--format ccm|cc-mesh`,
  `--final`, `--seen`, `--hop`, and `--participants`.
- If the `mesh-hydrate` command is available, run it with recipient labels and send its exact output.
- If only the bundled script is available, it self-locates and checks `participants.local.json` next to the installed skill, then `MESH_PARTICIPANTS_JSON`, `~/.config/...`, and `/etc/...`.
- Do not manually reconstruct a hydrated message after running a tool/script. If
  output is redacted or lacks deliverable Discord mentions, stop and use a
  send-and-hydrate path (`mesh_send` or `mesh-send-discord.mjs`) or report
  `BLOCKER: hydrated mentions not deliverable exactly`.
- Keep routing out of the body text; the body is only the human-readable message.
- New live smoke/tests should prefer compact `ccm:v1` envelopes when supported,
  while keeping legacy `cc-mesh:` compatibility.
- When recipients are present, the sent message must include the routing trigger
  generated by the tool/script and at least one real Discord mention.
- If hydration fails because a label is unknown or no participant config exists,
  do not send a routed reply. Report the missing label/config in plain language.

Recipient labels are local names configured outside the skill, such as `alice`, `reviewer`, or `ops-bot`. Use only labels present in the local participant config.

If you receive:

```text
cc-mesh: alice
<@Alice> Ask one yes/no question.
```

And you are `alice`, a normal reply to the sender should be hydrated to the sender's local label, unless you deliberately choose different or additional recipients.

Hydrate example:

```bash
mesh-hydrate --to facilitator --body "Is it commonly found in a home?"
mesh-hydrate --to agent-alpha --to example-tenant --body "Answer: yes."
mesh-hydrate --to agent-alpha,example-tenant --body "Answer: yes."
```

Manual fallback checklist:

1. Pick recipient labels from the local participant config.
2. Run `mesh-hydrate --to label1,label2 --body "message body"`.
3. Send the exact output from the command/script.
4. If the output has no Discord mention, stop and fix config before sending.

Bundled-script fallback:

```bash
node /path/to/mesh-discord-routing/scripts/mesh-hydrate.mjs --to facilitator --body "Is it commonly found in a home?"
```

`node scripts/mesh-hydrate.mjs` is a relative shell path: run it from the skill directory or provide the full path. The script itself behaves the same from any working directory.

The command/script outputs the Discord-ready message with `cc-mesh:` and mentions already composed. It requires a local config file such as `participants.local.json` or the `MESH_PARTICIPANTS_JSON` environment variable.

Session helper:

```bash
mesh-session start --session-id demo-channel --channel-id channel-id --participants agent-alpha,example-tenant --policy round_robin --active agent-alpha --turn-budget 12
mesh-session next --state state/demo-channel.json --from agent-alpha
mesh-session next --state state/demo-channel.json --from example-tenant --selected agent-alpha
mesh-session stop --state state/demo-channel.json --status completed --reason "task done"
```

Use `mesh-session` only as lightweight turn state. Supported policies are
`round_robin`, `facilitator_selected`, `participant_selected`, `random`,
`broadcast`, and `freeform`. For policies that require a choice, pass
`--selected` or `--to`; for `random`, the helper avoids returning the same
participant when another participant is available. Route only to the returned
`to` labels, then hydrate the final Discord message with `mesh-hydrate`.

If `mesh-session next` exits with `out-of-turn sender`, do not manually reply
anyway. Stay silent or ask the controller/facilitator to repair state. If it
exits with `turn budget exhausted`, stop the loop and request human/controller
input before continuing.
